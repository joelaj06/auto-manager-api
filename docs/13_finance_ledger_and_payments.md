# 13 — Finance, Ledger & Payments

> **Update 2026-10-13 (decision 16): tenants do not perform transactions through the system — they only *record* them.** Out of scope for tenants: payment gateways, payment links, Paystack/Hubtel webhooks, per-tenant provider keys, MoMo prompts, automatic confirmation (§3, and the `provider`/`pending` payment flow in §2.2). Kept: invoices, receipts, payment *recording* (cash, MoMo, bank, cheque noted by staff), allocations, ledger, cash sessions, optional reconciliation by importing a statement for comparison, multi-currency (doc 20). The gateway used for **our own** subscription billing is a separate platform concern, now designed in [25](25_platform_billing_and_subscriptions.md) (decision 27). Payment `status` is therefore `recorded → reversed`, and a recorded payment can carry the payer's MoMo/bank reference as free text. Revised VAT approach in §6.

## 1. Why a shared finance layer

Today money lives in five shapes: `Sale.amount`, `Rental.amountPaid/balance`, `WorkAndPay.amountPaid` + `PaymentRecord`, `Expense.amount`, and dashboard sums computed differently per module (H13). Adding dealer deals and purchases would make it nine. One pipeline gives:

- one receipt format, one cash-up, one MoMo reconciliation,
- consistent balances (derived, never typed in),
- trivial P&L per vehicle / branch / module,
- clean export to an accounting package.

## 2. Building blocks

```
Source documents          Money movement              Accounting view
(rental, deal, schedule,  payments (in/out)           ledger_entries (debit/credit,
 remittance, expense,  ─▶ payment_allocations    ─▶   tagged vehicle/branch/party)
 purchase cost)           invoices (receivables)       chart of accounts
```

### 2.1 Invoices (receivables)
Generated by rentals (on confirm/close), deals, W&P (optional — schedule rows can act as invoices), remittance shortfalls (optional), ad-hoc (e.g. damage charge). Status: `draft → issued → partially_paid → paid | void`. Credit notes for corrections.

### 2.2 Payments
- `direction`: in (customer/driver → us) or out (us → supplier/staff/refund).
- `method`: cash, MoMo, bank transfer, card, cheque, offset (trade-in / deposit application).
- `provider`: manual, Paystack, Hubtel, Flutterwave, bank feed.
- `status`: pending (e.g. MoMo prompt sent) → confirmed → reversed/failed.
- Receipt PDF + SMS on confirmation. Numbered via counters.

### 2.3 Allocations
A payment is split across one or more targets: invoice, W&P schedule rows, remittance, deposit, expense, purchase cost. Unallocated remainder = **customer/driver credit** (wallet) usable later.

### 2.4 Ledger (double-entry-lite)
- Every confirmed financial event posts balanced `ledger_entries` (Σdebit = Σcredit) with tags `{ vehicleId, branchId, partyId, module }`.
- Small system chart of accounts seeded per tenant: Cash, Bank, MoMo wallet, Accounts receivable, Customer deposits (liability), Accounts payable, Rental income, Remittance income, W&P income (+ deferred markup if desired), Vehicle sales income, COGS vehicles, Vehicle expenses (by category), Overheads, Depreciation, Vehicle assets, Accumulated depreciation.
- Posting rules are code (`postings/rentalClosed.ts`), unit tested.
- Not a full accounting product: no manual journals for normal users; export to QuickBooks/Xero/Excel journal format.

Example — rental closed with GHS 1,000 income, deposit 500 applied 200 / refunded 300:
```
Dr Customer deposits 500      Cr Rental income 1,000 (partly)
Dr Cash 800                   Cr Cash (refund) 300
...
```
(Exact postings defined at implementation.)

## 3. Payment integrations

| Provider | Use |
|---|---|
| **Paystack** | Payment links, MoMo + card collection, webhooks; platform subscription billing |
| **Hubtel / Flutterwave** | Alternatives for MoMo direct debit / USSD |
| MTN MoMo API (direct) | Lower fees at scale (V3) |

- Webhooks → `webhook_events` (idempotency by provider event id) → confirm payment → allocate per `metadata { targetType, targetId, tenantId }`.
- Tenant connects **their own** Paystack subaccount/keys (money goes to tenant, not platform). Store keys encrypted (KMS / libsodium sealed box).
- Payment links: `POST /payments/links { target, amount }` → short URL for SMS/WhatsApp.

## 4. Cash management

- **Cash sessions** per branch/cashier: opening float → payments in/out → expected vs counted → variance report.
- Bank deposits from cash (transfer between accounts).
- **Reconciliation**: import MoMo/bank statement CSV → auto-match by reference/amount/date → manual match UI for leftovers.

## 5. Multi-currency

> Full design in [20_currency_management.md](20_currency_management.md). Default base currency is **Ghana Cedi (GHS)**, selectable per tenant.

- Tenant base currency (GHS). Documents may be in USD/EUR (imports, some rentals).
- Store `amountMinor`, `currency`, `fxRate`, `amountBaseMinor`. Reports in base currency.
- FX rate table per tenant (manual daily entry; API feed later).

## 6. Taxes — Ghana VAT (decision 12, revised)

VAT is **optional per tenant** and driven by data, not hard-coded:

- `organisation.tax_settings`: `vat_registered` (bool), TIN, VAT number, tax scheme (`standard`, `flat_rate`, `exempt`), prices entered `inclusive` or `exclusive` of tax.
- `tax_codes` table (platform-seeded, tenant-extendable): code, name, components[] (e.g. VAT, levies), rate per component, **`effective_from` / `effective_to`**, compounding rule, applies-to (`sales`, `purchases`).
- Invoice/receipt lines reference a tax code; the code's rates **in force on the document date** are applied and snapshotted on the line (rate, amount) so later rate changes never alter history.
- Per-item defaults: e.g. vehicle sale vs rental vs service vs exempt supplies; tenant can override per product/line.
- Input tax (on purchases and expenses) can be recorded for VAT-registered tenants → VAT payable report (output − input) per period.
- Documents show TIN/VAT number and the tax breakdown required on a Ghanaian tax invoice. Confirm exact invoice requirements with GRA guidance.
- Withholding tax on supplier payments: optional field.

> **Rates must be verified before configuring.** Ghana's VAT regime has changed repeatedly (VAT, NHIL, GETFund levy, COVID-19 levy, flat-rate scheme). Do not hard-code rates; seed them from the current GRA/legislation with an accountant's confirmation, with effective dates so history stays correct.

## 7. Period close & integrity

- Lock periods (no edits before a locked date; corrections via reversal entries).
- Every money document immutable after confirmation; corrections via void/credit note/reversal → full audit trail.
- Nightly integrity job: Σ allocations ≤ payment amount; invoice balances = total − allocations; ledger balanced.
